# Integrity and Trade-Off Reflection

In the relational design, integrity is handled automatically. StudentID is a primary key on the Student table, and AdvisingNote and SupportVisit both use it as a foreign key. That means the database itself won't let a note or visit get created for a student who doesn't exist, and it won't let a required field like Date or StudentID come back empty. I don't have to write extra code to catch those problems. The database catches them for me before the bad data ever gets saved.

MongoDB doesn't give me that protection by default. Since notes and visits are embedded arrays inside the student document, there's technically nothing stopping a document from being missing a field, or having a note with a typo in the category, or a date stored in a different format than the rest. Because different documents in the same collection can have different shapes, it would be easy for the data to drift over time if five different people were entering it without agreeing on a format first. This connects to what Week 3 covered about flexible schemas: MongoDB doesn't enforce structure the way a relational database does, so the responsibility for keeping the data correct moves from the database to the team and the application code.

To protect integrity in MongoDB, I'd rely on a few things: schema validation rules at the collection level so MongoDB rejects a document that's missing a required field like studentId or date, application-level checks before anything gets inserted, and a shared convention the whole team agrees on for field names and formats (like always using YYYY-MM-DD for dates). None of that is automatic the way foreign keys are, so it takes more discipline to keep it consistent. This ties back to the CAP theorem too. MongoDB is built to stay flexible and available even as data grows across many documents, but that flexibility is a trade-off. Relational databases lean toward strict consistency and enforce it for you. MongoDB leans toward flexibility and hands that job to whoever is building on top of it.
